# VoiceMatch 架构思想深度解析

> 本文档深入讲解架构背后的**思考过程**：为什么这样分层、状态机如何设计、并发模型如何选择、匹配算法如何演进、以及系统如何从 200 元/月扩展到支撑百万用户。
>
> 配套文档：[设计思想](design-philosophy.md) · [系统架构](architecture.md) · [架构决策记录](adr/)

## 1. 架构的核心矛盾与解法

任何实时社交系统都面临一个核心矛盾：**状态要快（毫秒级）但也要可靠（不丢数据）**。

VoiceMatch 的解法是**双存储职责分离**：

```
┌────────────────────────────────────────────────────────┐
│                       Redis（快）                       │
│   在线状态 · 呼叫状态 · 匹配池 · 会话状态                │
│   ⚡ 毫秒级读写，支撑核心链路                            │
└──────────────────────┬─────────────────────────────────┘
                       │ 通话结束后异步归档
                       ▼
┌────────────────────────────────────────────────────────┐
│                      MySQL（稳）                        │
│   用户资料 · 通话记录 · 举报记录 · 黑名单                │
│   🔒 事务保证，支撑查询与合规                            │
└────────────────────────────────────────────────────────┘
```

**铁律**：
- 在线状态、呼叫状态、匹配池**禁止**写入 MySQL（性能灾难）
- 用户资料、通话记录**禁止**放入 Redis（数据丢失风险）
- 所有状态变更**必须先写 Redis**，通话结束后异步落 MySQL

## 2. 分层思想

架构按"职责边界"分为四层，每层只依赖下一层：

```
┌─────────────────────────────────────────────┐
│ 用户层   注册/登录 · 偏好设置 · 发起/接听/挂断  │
├─────────────────────────────────────────────┤
│ 匹配层   随机池(FIFO) · 同城(Geohash) · 目的地 │
├─────────────────────────────────────────────┤
│ 通话层   信令状态机 · RTC 传输 · 离线唤醒       │
├─────────────────────────────────────────────┤
│ 数据层   Redis(状态) · MySQL(持久化)          │
└─────────────────────────────────────────────┘
```

**为什么这样分层**：
- **用户层**：业务入口，无状态，可水平扩展
- **匹配层**：纯算法逻辑，输入匹配请求，输出配对结果，不感知通话细节
- **通话层**：核心状态机，处理呼叫生命周期，不感知匹配算法
- **数据层**：存储抽象，通过接口隔离，Mock 可替换（`internal/store` 提供接口 + Mock 实现，测试无需真实 Redis/MySQL）

## 3. 核心状态机设计

通话生命周期用**有限状态机**严格约束，不允许中间态跳跃：

```
             呼叫               接听
   idle ────────────► ringing ────────► connected ────────► ended
     ▲                 │  ▲               │
     │                 │  │               │
     │                 │  └── 拒绝/超时/取消 ┘
     │                 │
     └─────────────────┴── 取消呼叫（主叫侧）→ 回 idle
```

**状态定义**：

| 状态 | 含义 | 存储位置 | 进入条件 | 退出条件 |
|------|------|---------|---------|---------|
| `idle` | 空闲 | Redis hash | 登录成功/通话结束 | 发起呼叫 |
| `ringing` | 振铃中 | Redis hash | 匹配成功发呼叫 | 接听/拒绝/超时 |
| `connected` | 通话中 | Redis hash | 被叫接听 | 任一方挂断 |
| `ended` | 已结束 | Redis hash → MySQL | 挂断 | 归档到 MySQL |

**设计要点**：
1. **先写 Redis 再发信令**：状态是事实（source of truth），信令是通知。先落状态，再通知，避免"通知到了但状态没记录"的竞态
2. **TTL 兜底**：所有状态 key 设 TTL（如呼叫状态 60s），防止进程崩溃导致状态泄漏
3. **幂等**：`call_accept`/`call_end` 等操作可重复发送，状态机保证只生效一次
4. **MySQL 异步归档**：通话结束后由独立流程（或同进程异步协程）写 MySQL，不阻塞挂断响应

## 4. 并发模型

### 4.1 Go 服务端并发模型

```
┌────────────────── Signal Service (无状态) ──────────────────┐
│                                                             │
│   WebSocket 连接1 ──► goroutine1 ──┐                        │
│   WebSocket 连接2 ──► goroutine2 ──┤                        │
│   WebSocket 连接3 ──► goroutine3 ──┼──► Hub(注册表/广播)    │
│   ...                              │     │                 │
│   WebSocket 连接N ──► goroutineN ──┘     ▼                 │
│                                      Redis                 │
└─────────────────────────────────────────────────────────────┘
```

- **一连接一 goroutine**：Go 的 goroutine 栈起步 ~4KB，单实例轻松支撑 5 万+ 长连接
- **Hub 模式**：集中管理连接注册表，广播消息时遍历目标用户所在连接（借鉴 chat 应用经典模式）
- **无状态**：服务不保存任何跨请求状态，状态全在 Redis → 崩溃可重启，多实例可水平扩展
- **内存预算**：目标单实例 < 100MB（连接管理 + Hub），超出即触发扩容信号

### 4.2 事件驱动 vs 消息队列

早期**不引入 Kafka**，事件同步处理：

```
匹配成功 ──► 信令服务直接给双方推 match_found
呼叫     ──► 信令服务直接推 call_invite
挂断     ──► 直接写 Redis + 异步落 MySQL
```

**为什么可以这样**：一对一场景事件量小、无持久化需求、无跨服务异步解耦需求。等出现 IM 消息（需要持久化、需要离线重放）才引入 Kafka。

## 5. 匹配引擎设计

### 5.1 三种匹配模式

| 模式 | 数据结构 | 算法 | 复杂度 |
|------|---------|------|--------|
| 随机 | Redis List | LPOP 原子弹出两人 | O(1) |
| 同城 | Geohash 前缀 + List | 同前缀列表内 LPOP | O(1) |
| 目的地 | 城市标签倒排索引 + List | 按标签索引 LPOP | O(1) |

### 5.2 核心实现：动态池发现

匹配服务通过 **Redis 记录 user → pool 映射**，支持动态发现用户所在匹配池：

```
用户 A 加入同城池 ──► Redis: RPUSH pool:city:hangzhou userA
                       Redis: SET user:pool userA pool:city:hangzhou

匹配轮询 ──► SCAN 所有 pool:* key ──► 发现非空池 ──► LPOP 配对
```

**为什么不用固定轮询列表**：PRD 要求匹配池轮询频率固定 500ms 且不允许高频轮询。如果只轮询预定义的 random 池，同城/目的地模式就失效了。动态发现让任意新增的池子都能被匹配到。

### 5.3 超时与退出

- 匹配池中用户 **60 秒未匹配成功** → 自动出池（Redis 记录入池时间，轮询时校验）
- 用户取消 → 从所在池原子移除（通过 user→pool 映射找到池子再 LREM）
- 匹配成功 → 从池中原子弹出，保证**同一用户不会被匹配两次**

## 6. 可靠性设计

### 6.1 认证与安全

- WebSocket 连接通过 **JWT token** 认证（`?token=` 参数），服务端验证签名和过期时间
- token 中的 userID 作为信令操作的身份来源，防止身份伪造
- 401 拒绝未认证连接

### 6.2 离线唤醒

```
呼叫 B
 ├── B 在线 ──► WebSocket 直接推送 call_invite
 └── B 离线 ──► iOS: APNs VoIP Push (PushKit) ──► 唤醒 App ──► 建立 WS 连接
                Android: FCM + Telecom ──► 系统来电界面
```

### 6.3 失败场景

| 场景 | 处理 |
|------|------|
| 被叫无响应 30s | 呼叫超时 → 双方回 idle，主叫提示重新匹配 |
| 进程崩溃 | Redis TTL 自动清理状态；无状态服务重启即恢复 |
| WebSocket 断线 | 心跳检测 → 标记离线 → 通知对端 |
| 匹配池用户失联 | 60s 超时自动出池 |

## 7. 扩展路径（从 200 元/月到百万用户）

```
阶段 0 (MVP, ~200元/月)
  1× 2核4G 信令+匹配 │ 1× Redis │ 1× MySQL │ LiveKit 云
        │ 日活 > 1 万
        ▼
阶段 1 (增长期, ~300元/月)
  2× 信令 (无状态水平扩展) │ Redis 主从 │ Nginx 负载均衡
        │ 日活 > 10 万
        ▼
阶段 2 (规模化, ~800元/月)
  匹配服务独立拆分 │ Redis Cluster │ 多可用区
        │ 新需求
        ▼
阶段 3 (功能扩展)
  需要 IM → +Kafka + MongoDB
  需要多人通话 → +SFU (LiveKit 原生支持)
```

**关键洞察**：因为早期架构"无状态 + 存储分离"，扩展只是**加实例/加机器**，不需要改代码。这是架构设计红利的体现。

## 8. 客户端架构思想

### 8.1 服务层抽象（面向接口）

```
Services (接口)          Implementations (实现)
─────────────────        ─────────────────────
WebSocketService  ◄────  WebSocketServiceImpl
RtcService        ◄────  RtcServiceImpl
MatchService      ◄────  MatchServiceImpl
CallKitService    ◄────  CallKitServiceImpl
ApiService        ◄────  ApiServiceImpl
        │
        ▼
ServiceInjector (依赖注入容器)
```

**设计意图**：
- 页面只依赖接口，不感知实现细节 → 换 RTC SDK（LiveKit ↔ Agora）只改实现类
- `ServiceInjector` 统一装配 → 测试时可注入 Mock 实现
- 各服务职责单一：WebSocket 管信令、RTC 管音频、CallKit 管来电界面

### 8.2 页面流程（状态驱动）

```
LoginPage → HomePage → MatchWaitingPage → CallPage → EndPage
                          ▲                    │
                          └── 再匹配(1步) ──────┘
```

页面间通过路由参数 + 服务状态流转，不在页面间硬编码跳转逻辑。匹配成功由 MatchService 状态变化触发自动导航（最短路径原则）。

### 8.3 原生能力封装

- **iOS**：CallKit + PushKit（VoIP），锁屏接听
- **Android**：Telecom + FCM
- 统一封装在 `flutter_callkit_incoming` 插件背后，Flutter 侧只调 Dart API

## 9. 架构自检清单

提交任何架构变更前，用这份清单自检：

- [ ] 是否违反"交互链路最短"红线？（多一步操作？）
- [ ] 是否引入新中间件？理由是否充分？
- [ ] 状态是否先写 Redis？是否有 TTL 兜底？
- [ ] 服务是否保持无状态？
- [ ] 是否违反"单实例起步"原则？
- [ ] 是否影响上架合规？
- [ ] 契约变更是否同步更新 shared/protocol 双端？
