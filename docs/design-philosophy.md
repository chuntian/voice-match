# VoiceMatch 设计思想

> 本文档回答一个核心问题：**当需求、成本、质量发生冲突时，我们按什么原则做取舍？**
>
> 配套文档：[架构深度解析](architecture-deep-dive.md) · [系统架构](architecture.md) · [架构决策记录](adr/)

## 1. 一句话设计观

**VoiceMatch 是一个"被两条红线约束"的产品**——所有功能、所有技术选型、所有代码结构，都必须服务于"交互链路最短"和"服务端高性能低成本"这两条红线。任何违背红线的功能，宁可砍掉或后置。

```
             ┌──────────────────────────────┐
             │   一切决策围绕两条红线展开    │
             └──────────────┬───────────────┘
                            │
          ┌─────────────────┴─────────────────┐
          ▼                                   ▼
  ┌──────────────────┐              ┌─────────────────────┐
  │ 红线一            │              │ 红线二               │
  │ 交互链路最短       │              │ 服务端高性能低成本    │
  │ 打开→通话 ≤ 2 步  │              │ 最少中间件 / 最低成本 │
  └──────────────────┘              └─────────────────────┘
```

## 2. 两条红线详解

### 红线一：交互链路最短

**定义**：用户从打开 App 到进入通话，操作不超过 2 步。

| 用户目标 | 操作步数 | 路径 | 设计体现 |
|---------|---------|------|---------|
| 随机连麦 | 2 步 | 打开 App → 点"开始连麦" | 首页默认偏好已预设，零配置 |
| 同城连麦 | 3 步 | 打开 App → 点"开始连麦" → 选同城 | 设置页所有选项有默认值 |
| 再连一个 | 1 步 | 结束页点"再匹配一个" | 不打断使用节奏 |
| 接听来电 | 0 步 | CallKit/Telecom 系统界面直接接听 | 禁止 App 内弹窗确认 |

**取舍原则**：任何需要用户多操作一步的设计，都必须有充分的业务理由，否则不采纳。

### 红线二：服务端高性能低成本

**定义**：用最少的中间件和服务器撑起核心链路。

| 约束 | 具体要求 | 带来的成本收益 |
|------|---------|---------------|
| 不建 Coturn | RTC SDK 自带 STUN/TURN | 省一台中继服务器 + 运维 |
| 不建 SFU | 一对一用 P2P，失败 SDK 自动降级 | 媒体面零服务器成本 |
| 不引入 Kafka | 无 IM 持久化需求，事件同步处理 | 省一个中间件 |
| 信令无状态 | Go 服务不存本地状态，可水平扩展 | 单实例 2核4G 起步 |
| Redis 单实例 | 核心状态总量小，几 GB 足够 | 约 50 元/月 |
| MySQL 单实例 | 只存用户资料和通话记录 | 约 50 元/月 |

**早期月成本合计约 200 元**，且按日活增长逐级扩展，每一级扩展都有明确触发条件（见第 5 节）。

## 3. 金字塔决策模型

整个项目的决策遵循"金字塔"结构——顶层是结论，中层是依据，底层是约束。

```
         ┌──────────────────────────────────────┐
         │ 结论：Flutter + RTC SDK + Go + Redis/MySQL │
         └──────────────────┬───────────────────┘
                            │ 支撑
          ┌─────────────────┼─────────────────┐
          ▼                 ▼                 ▼
  ┌─────────────┐   ┌─────────────┐   ┌─────────────┐
  │ 交互链路最短  │   │ 高性能低成本  │   │ 合规可上架  │
  └─────────────┘   └─────────────┘   └─────────────┘
          │                 │                 │
          ▼                 ▼                 ▼
  ┌─────────────┐   ┌─────────────┐   ┌─────────────┐
  │ 一键进池     │   │ 不建媒体服务 │   │ 公司主体+四证│
  │ 自动呼叫     │   │ 单实例起步   │   │ 举报机制     │
  │ 一键再匹配   │   │ 按需扩展     │   │ 避开敏感用语 │
  └─────────────┘   └─────────────┘   └─────────────┘
```

**决策时的提问顺序**：
1. 这个功能是否违反红线一（多一步操作）？
2. 这个技术是否违反红线二（多一个中间件/服务器）？
3. 是否影响上架合规？
4. 如果都不违反，再评估业务价值。

## 4. 核心取舍案例

### 4.1 为什么是 Flutter 而不是原生双端？

| 方案 | 开发成本 | 维护成本 | 决策 |
|------|---------|---------|------|
| Flutter 一套代码 | 1 套 Dart | 1 套代码 | ✅ 采用 |
| iOS Swift + Android Kotlin | 2 套代码 | 2 套代码 | ❌ 违反成本红线 |

代价是：部分平台特性（CallKit/PushKit/Telecom）需要写原生桥接代码，但通过 `flutter_callkit_incoming` 等成熟插件封装，代价可控。

### 4.2 为什么是 LiveKit 而不是自建媒体服务器？

| 方案 | 服务器成本 | 运维成本 | 决策 |
|------|-----------|---------|------|
| LiveKit 云服务 | 按用量，早期几乎为 0 | 零运维 | ✅ 采用 |
| 自建 Coturn/SFU | 需要 1+ 台服务器 | 高 | ❌ 违反红线二 |

LiveKit 自带：STUN/TURN、DTLS/SRTP 加密、拥塞控制、iOS/Android SDK。

### 4.3 为什么早期禁止 Kafka/RabbitMQ？

一对一语音场景没有 IM 消息持久化需求，匹配/呼叫事件都是"即发即用"，同步处理即可。引入消息队列会增加：一个中间件、一套运维、一个故障点。等出现"需要 IM 消息"的真实需求再引入。

### 4.4 为什么匹配服务早期与信令合并？

PRD 规划了独立的 `cmd/match`，但早期用户量小，匹配逻辑（Redis LPOP）本身极轻。合并部署可省一台服务器；代码层面仍保持模块独立（`internal/match`），后续拆分零成本。

## 5. 扩展触发机制

**原则**：不预支成本，用真实数据触发扩展。

| 触发条件 | 加什么 | 预估成本增加 |
|---------|--------|-------------|
| 日活 > 1 万 | Redis 主从、信令服务多实例 | +100 元/月 |
| 日活 > 10 万 | 匹配服务独立拆分、Redis 集群 | +500 元/月 |
| 需要 IM 消息 | 加 Kafka + MongoDB | 视规模 |
| 需要多人通话 | 加 SFU（LiveKit 天然支持） | 视规模 |

**为什么这些阈值是合理的**：
- 日活 1 万时，在线用户约 500-1000，Redis 单实例完全无压力，但为容灾开始做主从
- 日活 10 万时，匹配 QPS 约 2000/s，Redis 集群避免单点
- 一对一通话不需要 SFU 转发（P2P 直连），多人通话才需要

## 6. 最短路径全链路验证

```
注册（Apple ID 一键）→ 首页 → [开始连麦] → 匹配等待 → 通话 → 结束页 → [再匹配一个]
   │                   │        │            │        │        │
   │                   │        │            │        │        └─→ 直接回匹配等待（1 步）
   │                   │        │            │        └─────────→ 对方挂断
   │                   │        │            └────────→ 超时(60s) → 提示扩大范围/返回
   │                   │        └────────────→ 直接进池，无需二次确认
   │                   └────────→ 默认偏好已预设
   └────────────→ 登录成功即进首页
```

**关键设计决策**：
1. **匹配成功自动呼叫**——禁止"匹配到人了，是否开始通话"的二次确认弹窗
2. **来电用系统界面**——CallKit/Telecom 锁屏可接，禁止 App 内弹窗
3. **取消匹配回首页**——不允许回设置页，避免用户陷入配置循环
4. **结束页一键再匹配**——不回首页再进，保持使用节奏

## 7. 成本哲学

### 7.1 每月成本预算（早期）

| 资源 | 配置 | 月成本 |
|------|------|--------|
| 信令服务 | 2核4G × 1 | ~100 元 |
| Redis | 1核2G × 1 | ~50 元 |
| MySQL | 1核2G × 1 | ~50 元 |
| RTC SDK | 按用量 | 早期几乎为 0 |
| 推送 | APNs/FCM 免费 | 0 |
| **合计** | | **~200 元/月** |

### 7.2 成本控制原则

1. **能复用就复用**：RTC 云服务替代自建媒体服务器
2. **按用量付费**：不提前包年包月
3. **单实例起步**：不提前上集群、不分库分表
4. **无状态优先**：信令无状态 → 天然支持水平扩展 → 需要时才加实例
5. **砍掉不必要**：任何中间件必须回答"为什么现在需要"

## 8. 设计思想 FAQ

**Q：为什么不直接用现成的陌生人社交产品？**
A：产品目标是验证"最短链路语音连麦"这一核心体验，技术目标是低成本跑通全链路。

**Q：为什么不一开始就用微服务？**
A：违反红线二。早期 2 个 Go 服务 + 2 个存储，就是最简单的可运行架构。微服务是扩展手段，不是起步形态。

**Q：LiveKit 自托管与云服务怎么选？**
A：早期用云服务（省运维）；用户量稳定后可迁移到自托管（省成本），代码层通过 `livekit_client` SDK 无感切换。

**Q：信令为什么用 WebSocket 而不是 HTTP 轮询？**
A：呼叫/接听/挂断是低延迟、双向、事件驱动的通信，HTTP 轮询延迟高、浪费带宽、无法服务端主动推送。WebSocket 是唯一正确选择。

**Q：为什么状态先写 Redis 再异步落 MySQL？**
A：通话状态（在线/呼叫中/通话中）要求毫秒级读写，Redis 合适；通话记录（历史数据）要求持久化，MySQL 合适。两者职责分离，Redis 是权威状态源，MySQL 是最终归档。
